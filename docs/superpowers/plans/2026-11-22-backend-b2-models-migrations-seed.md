# Backend B2: Database Models, Migrations and Seed Data — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the FastAPI backend a complete SQLAlchemy schema for every entity in the SRS ERD, one Alembic migration that creates it on Neon, camelCase Pydantic schemas matching `src/api/types.ts`, and a re-runnable seed script with one demo user per role.

**Architecture:** One SQLAlchemy model module per feature area under `backend/app/models/`, mirrored 1:1 by a Pydantic schema module under `backend/app/schemas/`. All model/schema tasks are structurally tested (table columns/constraints, schema camelCase round-trip) without a live DB connection, so they can be written and verified incrementally. A single autogenerated Alembic migration is produced only after every model exists, then applied to Neon. Only after the migration lands do integration tests (real inserts, constraint violations, the seed script) run, using a per-test rolled-back transaction so the shared dev database stays clean.

**Tech Stack:** SQLAlchemy 2 (async) + asyncpg, Alembic, Pydantic v2 (`alias_generators.to_camel`), passlib[bcrypt], pytest + pytest-asyncio + httpx (all already pinned in `backend/requirements.txt`). New dependency: `email-validator==2.2.0` (required by Pydantic's `EmailStr`), added to `backend/requirements.txt` with a one-line reason in the task that needs it.

**Spec:** the pasted B2 task description (models for every ERD entity, one migration, camelCase schemas, seed script, tests) plus `CLAUDE.md` (Backend section) and `src/api/types.ts` (field names/shapes to match). `docs/DengueGuard_BD_SRS.pdf` §5.4 ERD (Figures 5.18a/b) is diagram-only (no extractable text/images in this environment — no PDF renderer installed); entity shapes are derived from `src/api/types.ts` and the task's own entity list instead.

## Review Focus

- **Donor contact leakage.** The task explicitly says a donor's phone must never be exposed before they accept a request. If `DonorProfile`'s default/public schema includes a raw `phone` field, any later endpoint built on it leaks contact info by default. → Task 7 gives `DonorProfile` schemas with a masked-phone read variant and a test asserting the masked schema has no raw phone field.
- **Seed re-run duplicates.** The task requires `python -m app.seed` to be safe to run twice. A naive `session.add(...)` + commit on every run double-inserts everything on a second pass. → Task 14 uses `ON CONFLICT (id) DO NOTHING` and a test that runs `seed()` twice and asserts row counts are unchanged after the second run.
- **DB constraints silently not enforced.** SQLAlchemy will happily let a `CheckConstraint` or `UniqueConstraint` be defined in Python but never show up in the DB if the migration autogenerate missed it (e.g. check constraints are sometimes skipped by naive autogenerate). → Task 13 inserts intentionally-bad rows (`booked_count > capacity`, `general_available > general_total`, a duplicate `(user_id, slot_id)` appointment) against the **real migrated DB** and asserts each one raises `IntegrityError`, not just that Python didn't complain.
- **camelCase / nested `LocalizedText` drift.** Every schema in `src/api/types.ts` nests bilingual text as `{ en, bn }`; it's easy to instead emit `nameEn`/`nameBn` flat keys from an ORM-mirroring schema. → Task 1's `CamelModel`/`loc()` helper is exercised by a schema test per entity that dumps `model_dump(by_alias=True)` and asserts the exact key shape (`"name": {"en": ..., "bn": ...}`), not just that it doesn't error.
- **AuditAction enum drift from the frontend.** `src/api/types.ts` already enumerates 29 `AuditAction` string literals that future phases will log against; typo-ing or dropping one here means an audit-writing call in a later phase fails silently or mismatches the frontend. → Task 11 defines `AuditAction` as an exact copy of the 29 values and a test that diffs the Python enum's values against that literal list (hardcoded in the test from `types.ts`).
